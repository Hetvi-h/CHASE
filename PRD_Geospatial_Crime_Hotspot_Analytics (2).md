# PRD: Geospatial Crime Hotspot & Community Safety Analytics

**Type:** College Community Engagement Project (solo build, AI-IDE / prompt-based development)
**Alignment:** SDG 11 (Sustainable Cities & Communities), SDG 16 (Peace, Justice & Strong Institutions)

---

## 1. Problem Statement

Local authorities and citizens lack an accessible, data-driven way to answer:
- Where do crimes concentrate geographically — nationally, by state, by city, and within a city?
- When (time of day / day of week) do they peak?
- Which crime types dominate in which areas?
- How do residents *perceive* safety, and does that match the data?
- What concrete interventions (patrolling, lighting, CCTV, awareness) would help most, where?

This project is a FastAPI + React application, backed by a geospatial data pipeline and ML layer,
that answers all five using a validated, NCRB-calibrated incident dataset with sub-city hotspot
zones for all 29 covered cities, plus a simulated safety-perception survey.

## 2. Data Provenance — Full Honesty Chain (read this before anything else)

This section exists because the project's data went through a real validation process worth
being transparent about — it is a strength of the methodology, not a flaw to hide.

1. **Base incident data**: Kaggle "Indian Crimes Dataset" (40,160 rows, 29 Indian cities, 2020–2024,
   14 crime-type categories, victim demographics, weapon, police deployed, case status).
2. **Validation finding**: cross-checking this dataset's per-city row counts against real NCRB
   "Crime in India 2023" official figures showed the Kaggle dataset's absolute volume is only
   0.1%–1.9% of real crime volume per city, and — with only a narrow sample of similarly-sized
   cities — its city-to-city proportions initially looked uncorrelated with real data. Testing
   across the FULL range of matched cities (11 mid-tier + 16 megacities, 27 of 29 total) revealed
   a real, moderate correlation (r ≈ 0.73) between Kaggle row counts and real NCRB totals — so the
   dataset is a **small, realistic-but-imperfect illustrative sample**, not fabricated noise, and
   not raw government microdata either (India does not publish real incident-level crime data
   publicly at street-address granularity — this is a genuine limitation, not a project shortfall).
3. **Correction applied**: incident counts per city were rescaled so each city's SHARE of the fixed
   total (~39,000 rows across matched cities) matches its real NCRB share — e.g. Delhi's real
   crime volume is ~36% of the matched-cities total, so Delhi's row count was raised to ~36% of the
   dataset accordingly, and over-represented cities were trimmed down. New rows for under-represented
   cities are generated by resampling whole rows (with replacement) from that same city's own
   existing rows — never inventing new attribute combinations from nothing.
4. **Result**: every row carries an `Is_Synthetic_Row` flag — `False` for original Kaggle rows,
   `True` for rows added during rescaling. This makes the real-vs-added split auditable at the row
   level, not just asserted in a paragraph.
5. **Sub-city positioning**: since no public dataset gives street-level incident coordinates for
   India, every row's exact `Latitude`/`Longitude` within its city is synthetically assigned via a
   weighted hotspot-mixture model (Section 6) — this applies to ALL rows, real and added alike,
   since even the original Kaggle rows only ever specified a city, never a sub-city location.

**Report language to use, verbatim or close to it:**
> *"Incident-level crime microdata is not publicly available in India. We used a Kaggle-sourced
> illustrative incident dataset, validated its per-city distribution against official NCRB 2023
> statistics (initial correlation r≈0.73 across 27 matched cities), and rescaled city-level row
> counts to match real NCRB proportions while preserving realistic per-incident attribute patterns.
> Sub-city coordinates are synthetically assigned via a hotspot-mixture model, since no public
> source provides street-level incident locations. A row-level `Is_Synthetic_Row` flag distinguishes
> original from rescaling-added records throughout."*

## 3. Data Pipeline (already executed — see combined_pipeline.py)

```
crime_dataset_india.csv (raw Kaggle, 40,160 rows, 29 cities)
        │
        ▼ STEP 1-2: real city->state mapping + geocode real city centroids (Nominatim)
        │           adds: State, City_Latitude, City_Longitude
        ▼ STEP 3: rescale row counts per city to match real NCRB 2023 proportions
        │         (27 of 29 cities matched to real NCRB totals; Kalyan & Thane left as-is)
        │         adds: Is_Synthetic_Row
        ▼ STEP 4: generate 3-6 weighted hotspot zones per city + assign every row a
        │         synthetic Zone_ID/Latitude/Longitude (Cyber Crime spread city-wide,
        │         other crime types clustered at hotspot centers)
        ▼
crime_dataset_india_final.csv   (main table — this is crimes_master)
zone_reference.csv              (hotspot zone geometry — ~90-170 zones across 29 cities)
```

CPU only throughout — no GPU/TPU needed anywhere in this pipeline (network-bound geocoding,
lightweight resampling, vectorized numpy positioning — none of it is tensor/matrix-multiplication
work that would benefit from acceleration).

**Not yet generated**: `survey_synthetic.csv` (the safety-perception survey) — build this directly
during the Antigravity build, since it needs no internet/geocoding, just documented distribution
logic (Section 7).

## 4. Tech Stack

| Layer | Choice | Rationale |
|---|---|---|
| Data pipeline | Python, Pandas, NumPy, geopy — Colab, CPU | Already executed per Section 3 |
| Backend | **FastAPI** | Async REST API, auto Swagger docs |
| Database | **Supabase-hosted PostgreSQL + PostGIS** | Managed, free-tier, PostGIS enabled via one SQL command — no local server install/admin. Same connection string works in dev and after deployment. Real geospatial queries: point-in-polygon, nearest-hotspot, multi-level aggregation |
| Frontend | **React (Vite) + react-leaflet + Recharts + Tailwind** | Leaflet for maps at every zoom level, Recharts for charts |
| Hotspot ML | DBSCAN/HDBSCAN + KDE (scikit-learn) — optional refinement of the already-generated zones | Density-based clustering, not classification |
| Risk prediction | Random Forest (scikit-learn); features: Zone_ID, hour, day_of_week, month | Genuine supervised-ML component; also the Risk Predictor demo feature |
| Deployment | Backend: Render/Railway free tier · Frontend: Vercel | Free, public demo link |

**Not using deep learning** — nothing in this pipeline or app is a tensor/sequence workload that
would benefit from it; DBSCAN + KDE + Random Forest is the honest, defensible ML story.

## 5. Application Features

Single-page app, scroll/tab **sections**:

1. **Multi-Level Map** — country view (real state-level aggregate dots) → zoom into a state → real
   city-level dots → zoom into any city → every incident plotted at its Zone_ID position, with
   DBSCAN/heatmap overlay. This now works for **all 29 cities**, not just one flagship city, since
   the hotspot-mixture zone method generalizes cleanly across all of them.
2. **Time-Slider Animation** — drag through 24 hours, watch density shift live (precomputed hourly
   density grid per zone).
3. **Zone Safety Ranking** — zones ranked by composite safety score (Section 6).
4. **Recommendations Panel** — rule-based cards per zone.
5. **Risk Predictor** — pick a zone + time → Random Forest returns predicted risk level + likely
   crime type.
6. **About/Methodology panel** — states plainly, per Section 2: which rows are original vs
   rescaling-added (`Is_Synthetic_Row`), that all coordinates are synthetically positioned, and
   the r≈0.73 NCRB validation result. Keep this visible, not buried.

## 6. Analytics & ML Details

- **Hotspot zones**: already generated per city (3–6 weighted centers, Section 3 Step 4) — can be
  refined in-app with DBSCAN/KDE on the resulting point cloud if time allows.
- **Composite Safety Score** (0–100 per zone):
  `score = 100 - (w1 * normalized_crime_density + w2 * (5 - avg_survey_rating)*20 - w3 * lighting_proxy)`
  State and justify chosen weights explicitly.
- **Risk Predictor**: Random Forest, features = Zone_ID, hour, day_of_week, month; report
  accuracy/F1 + confusion matrix in the About panel.
- **Recommendation engine**: plain `if/elif` rule table.

## 7. `survey_synthetic` — to be generated during the Antigravity build

No external data needed — build with numpy/pandas directly in the backend's data-prep step.

**Generation logic**: ~10,000–20,000 rows, distributed across all zones in `zone_reference.csv`.
For each zone, sample `safety_rating` (1–5) from a distribution whose mean is inversely related to
that zone's real-adjusted crime density (higher crime density → lower mean safety rating, plus
random noise) — this ties the survey to the real, NCRB-calibrated crime data rather than being
pure noise. Document the exact weighting formula used in code comments and in the About panel.

**Exact schema:**
```
survey_id                     BIGINT    PRIMARY KEY
Zone_ID                       VARCHAR   -- FK to zone_reference
respondent_age_bracket        VARCHAR   -- '18-24','25-34','35-49','50+'
respondent_gender             VARCHAR
time_of_day_band              VARCHAR   -- Morning/Afternoon/Evening/Night
safety_rating                 INT       -- 1-5
primary_concern                VARCHAR  -- theft/harassment/poor_lighting/reckless_driving/other
visits_after_dark_frequency   VARCHAR   -- Never/Rarely/Sometimes/Often
suggested_improvement         VARCHAR   -- CCTV/patrolling/lighting/awareness_programs/other
response_date                 DATE
```
